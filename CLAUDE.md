# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # Start dev server (Next.js + Turbopack on port 3000)
npm run build      # Production build
npm run lint       # ESLint
```

> **Windows SSL note:** The dev script runs `cross-env NODE_OPTIONS=--use-system-ca next dev`. This is required because Node.js's built-in fetch (undici) does not trust the Windows system certificate store by default, which causes all Supabase calls to fail with `UNABLE_TO_VERIFY_LEAF_SIGNATURE`. Do not remove `cross-env NODE_OPTIONS=--use-system-ca` from the dev script.

### Auth flow

Auth is **cookie-based, not Supabase SSR**. The login API route (`/api/auth/login`) calls `signInWithPassword` and manually sets `sb-access-token` and `sb-refresh-token` cookies. The middleware (`src/middleware.ts`) checks for `sb-access-token` on every non-public route.

- Use `createSupabaseBrowserClient()` (anon key) for auth operations like `signInWithPassword`
- Use `createSupabaseServerClient()` (service role key) for admin operations like `createUser` or direct table writes
- The app layout (`src/app/(app)/layout.tsx`) reads the cookie manually and calls `supabase.auth.setSession()` to rehydrate the client-side session
- **The cookie is REWRITTEN on every app load + on `TOKEN_REFRESHED`** (`writeSessionCookies` in the app layout). Fixed Aug 6 2026: the cookie had a 7-day maxAge and was only set at login, while the Supabase client silently refreshed the token in localStorage against a 30-day refresh token — so exactly 7 days after login the cookie died with the session still valid: the UI looked signed-in (name comes from localStorage) but every API call failed.
- **Middleware answers API routes (`/api/*`) with a JSON 401 `{errorCode:"SESSION_EXPIRED"}`** instead of redirecting to `/login` — `fetch()` silently follows redirects, so users were getting `Unexpected token '<', "<!DOCTYPE"... is not valid JSON` on every page instead of "Session expired". Page routes still 307 to `/login`. `/manifest.webmanifest` + icons are PUBLIC_PATHS (a login-redirected manifest kills the PWA "Install app" prompt).

### Plan gating

Plans are `trial | pro | premium` (defined in `src/lib/types.ts`). Business mode requires `premium`. The `UpgradeModal` component is shown when a locked feature is accessed. `PLAN_LIMITS` and `PLAN_PRICES` in `types.ts` are the source of truth.

### Shared data pattern (Pages & Store)

Pages & Store data flows through a React Context, **not** direct imports:

- `src/lib/pages-store.tsx` — `PagesProvider` (mounted in `src/app/(app)/layout.tsx`) holds the live list in state. Source of truth = Supabase `store_pages`; `localStorage` `pesowise_pages` is a same-session read cache that paints instantly, then gets refreshed.
- Consume with `usePages()` (full CRUD) or `useActivePages()` (non-archived only). The business dashboard and ROAS Tracker both read pages via `useActivePages()` — this is how a store's Pancake credentials reach those modules.
- `src/lib/pages-data.ts` only defines the `PageStore` type and the original seed array (now only used as a first-run fallback).
- ⚠️ **`useActivePages()` returns a FRESH array every render.** Key fetch effects off a value string (e.g. `pagesKey`), never off array identity, or you get an infinite fetch loop.

A page is "connected" to the dashboard/ROAS when it has both `api_key` and (`pancake_page_id` or `shop_id`).

### Pancake POS integration

The business dashboard and ROAS Tracker pull real order data from Pancake POS Open API via the server-side proxy `src/app/api/pancake/orders/route.ts` (keeps credentials server-side, avoids CORS). `src/app/api/pancake/debug/route.ts` is a diagnostic endpoint for inspecting raw Pancake responses.

Non-obvious facts (verified against a live shop — do not "simplify" these away):

- **Base URL / endpoint:** `https://pos.pages.fm/api/v1/shops/{SHOP_ID}/orders`. Auth is the `api_key` query param. The client passes the shop ID as the `page_id` query param to our route.
- **Date filter:** `startDateTime`/`endDateTime` are **Unix timestamps** (not `from_date`/`to_date`), plus `updateStatus=inserted_at`. `toUnix()` converts `YYYY-MM-DD` to a PHT (UTC+8) timestamp. Pagination uses `page_number` + `page_size` (max 100), not `page`.
- **`status` is a number, `status_name` is the string.** Verified primary status codes: `0` new, `1` confirmed, `2` shipped, `3` delivered, `4` returning (For Return), `5` returned, `6` canceled (Unfulfilled), `7` removed (excluded from totals), `8` packaging, `9` waiting-for-pickup, `11` restocking.
- **In Transit / On Delivery are courier sub-statuses, not primary statuses.** They live in `order.partner.partner_status` (`on_the_way` = In Transit, `out_for_delivery` = On Delivery, `undeliverable` = problematic). These can't be filtered server-side, so they're tallied by paginating all orders.
- **Sales = the `cod` field.** ⚠️ **COUNTS and MONEY come from different places, on purpose.** Counts use the one-row `filter_status[]` aggregates (`total_entries` — authoritative, not pagination-limited). **Money must NEVER come from `aggs.cod.value`**: it is summed server-side by Pancake, so the 100× SCALE guard (which needs per-order item prices) cannot reach it. Live proof (Aug 6 2026): the same 83 parcels read **₱146,512** via the aggregate but **₱47,710** via pagination — one order storing ₱998 as ₱99,800 inflated everything 2.6×. All displayed money therefore comes from `response.exact`, computed per-order in `phase=full` where `descale()` applies. `fetchStatusAgg`'s `sales` field is kept only because `byDate`/ROAS predate this; treat it as diagnostic, not displayable.
**THE INVENTORY WAS RESET ON AUG 20 2026** (owner order: "reset tayo, PPW 0"). `product_batches` and `stock_releases` were emptied, `product_items` counts (goods/damage/loss/released) zeroed — the item catalog itself (SKU/name/COG/supplier) was kept. Full pre-reset backup lives in the session scratchpad (`inventory-backup-2026-08-20T07-30-21`). Two structural changes made the reset durable: ⚠ **the `supa-rows` cache→DB backfill was removed** — it re-uploaded a browser's localStorage into any *empty* table, which meant a wiped table resurrected on the first machine with a stale cache (an empty table is now an answer, not a mistake to fix); and **PPW resets by date-line, not deletion** — PPW is computed live from Pancake (waybill assigned but not picked up), so nothing can be deleted to zero it; the `inventory_resets` table (migration **0032**) cuts off orders before the reset so PPW starts at zero and only grows with new waybills. ⚠ **Its RLS is split on purpose**: SELECT is member-wide (every machine's PPW must share the same line) but INSERT/UPDATE/DELETE require the business owner or a `business_users.mother` account — owner ruling ("admin lang ang may access"), enforced by the database, not the UI.

**NEW UNIT CODES ARE CREATED WITH NEGATIVE-INVENTORY SALE OFF** (owner ruling, Aug 21 2026, with a screenshot of the toggle) — a unit code is a *bundle*: its real stock lives in the component items in PesoWise, so letting POS sell it past zero is selling what isn't there. The sync sends `is_sell_negative_variation: false` on the variation **and** `is_sell_negative: false` on the product — on create, on the name-only fallback, **and on every edit**; without the edit case the first rename silently switches it back on. ⚠ The switch lives on the **variation**, not the product, and writing it requires the **enveloped** `{ product: … }` PUT — the plain body answers "Server internal error" 400. Both verified live. ⚠ **This is NOT `is_hidden`**: an earlier pass read "naka off" as hiding and set `is_hidden: true`, which removes the product from POS altogether; that was wrong and has been reverted (code and the one already-hidden product). ⚠ The second toggle in that screenshot — **"Out-of-stock warning by product" — is not reachable through the API**: seven candidate field names (`is_out_of_stock_warning`, `out_of_stock_warning`, `warning_out_of_stock`, `is_warning_out_of_stock`, `alert_quantity`, `warning_quantity`, `min_quantity`) were each accepted with HTTP 200 and silently dropped, and none comes back in the product payload. It stays a manual setting in Pancake until someone names the real field.

**A UNIT CODE GOES ONLY TO THE PAGES YOU PICK — PAGE SELECTION IS REQUIRED** (owner-reported, Aug 20 2026: three unit codes appeared on *every* Pancake POS page). The old rule was `input.pages.length ? filter(...) : connectedPages` — **blank meant "all connected pages"**, so forgetting to choose broadcast the code across all 24 shops. Spreading everywhere must be a choice, never the consequence of an omission. Submit now blocks an empty selection (along with Selling Price), the sync targets **only** the picked pages, and if a blank somehow reaches it the push goes to **none**, not all. ⚠ The Excel upload path builds `pages` from a column too — an empty Pages cell there is likewise "no pages", not "every page".

**PANCAKE custom_id/barcode IS UNIQUE ACCOUNT-WIDE, NOT PER PAGE** — pushing a unit code whose name is already held as a barcode by *any* page in the Pancake account (including pages not connected to PesoWise, and deleted products that still reserve it) fails with "Variation … already exists in the system", and the product simply never appears on the target POS page (owner-reported Aug 20 2026: "Lumyra x2" was in no connected catalog yet still rejected). The sync route now retries **by name only** — no custom_id, no barcode — when it sees that rejection; the POS staff pick by name and our own update/delete matching accepts name OR custom_id, so nothing downstream breaks. The reply carries a `note` saying the product has no custom_id. ⚠ Also observed: Pancake's **plain (un-enveloped) POST body answers "Server internal error" HTTP 400** on this endpoint; the `{ product: … }` envelope is the one that actually works — keep the envelope fallback.

**SUPPLIER TRUE COSTS ARE OWNER-ONLY — A DIFFERENT LOCK THAN EVERYTHING ELSE** (owner request, Aug 20 2026). The owner is his own supplier: the declared COG everyone sees (₱27) sits above what he really paid (₱25), and the gap is his private margin. `supplier_true_costs` (migration 0031) is the **only table whose RLS has no `is_business_member` branch** — owner (`businesses.owner_id = auth.uid()`) only, so staff get zero rows even hitting the endpoint directly with the anon key. ⚠ Never "fix" its policy to match the others; the mismatch is the feature. Three layers, each with a distinct job: RLS (the lock), `useIsOwner()` — a real `auth.getUser()` check, **not** `isMotherAccount()` which is spoofable localStorage — gates rendering so non-owners see *nothing, not even a placeholder* (a "Private" box is an invitation); and an eye toggle masks amounts even for the owner (screens get shared). Margin math is **per received batch** — Σ(batch.cog − true_cost) × qty — because declared prices change over time and using the current COG would rewrite history. The declared COG stays in `product_items`/`product_batches` where staff can see it; only the true price lives in the locked table, so a leak requires a row from it.

**SUPPLIER NAMES ARE ADMIN-ONLY** (owner ruling, Aug 19 2026) — warehouse staff must not see them **anywhere, including exports**. ⚠ The old `Confidential` masking was *hiding, not denying*: any user could click the eye. It now takes a `locked` prop that renders the mask with **no button, no title, and the value never entering the DOM** — so Inspect Element yields nothing. Gated on `isMotherAccount()` in Product Items (table cell, column filter, page-level Show toggle, view screen, add/edit form) **and** the Inventory Dashboard's "Inventory Value by Supplier" pie, whose slice labels spell the names out in full — locking the column while leaving that chart open would have been theatre. ⚠ The Excel export **drops the column entirely** rather than blanking it: a blank column still signals that something is withheld, and a blank is one edit away from being wrong. Receive Stock picks the supplier from a **dropdown** of registered suppliers (free text made "MBF Skincare", "MBF skincare" and "MBF  Skincare" three different suppliers that never reconcile with Purchase Order); a stored value no longer in the list is still shown, tagged, so saving cannot silently blank it.

- ⚠️ **THE 100× GUARD IS PER-ITEM WHEN AN ORDER IS MIXED.** `orderIsScaled` is all-or-nothing by design — it refuses to guess when unit prices disagree. But at the **order total** that refusal is not caution: an order holding one broken item (49,900) and one correct item (499) displayed **₱50,399** instead of ₱998 (owner-reported, Aug 19 2026 — Velora Care, "1x Velora Care, 1x Velora Care"). `mixedScaleTotal()` recomputes the total item by item in that case only, halving what looks broken and leaving what looks right. ⚠ It must be applied in **both** money paths — `toRow` *and* the `wantFull` exact-totals loop — or the table and the Dashboard give two different answers for one order. Measured across **13,088 orders on 24 pages**: zero currently mixed and zero displaying ≥₱10,000, so this guards a case that has happened rather than one happening now; the uniform-price majority is untouched.
- **`response.exact`** (phase=full) = per-status counts + descaled money, **cancelled (status 6) excluded** — the same rule `byDate` uses, so the TOTAL SALES card and its breakdown modal always agree. Also carries `rescaledOrders`/`rescaledExcess` (surfaced as an amber banner — the 100× correction is never silent) and `response.truncated` (range exceeded `MAX_PAGES`×100 = 20,000 orders → money is UNDERSTATED, red banner).
- **`?status=6,8`** limits phase=full pagination to given statuses — how "Unfulfilled / Last Month" gets descaled money for a whole month without paginating every order in it.
- **Dashboard card formulas:** Total RTS = returning + returned; **Unfulfilled = packaging (status 8)** — not canceled; Fulfilled = delivered + shipped + waiting-for-pickup. **Total Sales excludes cancelled** (user decision, Aug 7 2026 — cancelled is not income).
- **Dashboard paint order:** phase 1 paints COUNTS only (instant, aggregate-derived); every peso figure shows a spinner until phase 2 lands. Showing the aggregate amount first and correcting it later was rejected — a finance card that jumps from ₱154,778 to ₱55,976 destroys trust more than a 2-second wait.

### UI conventions

- **`DateRangePicker`** (`src/components/business/PancakeDatePicker.tsx`) = the standard date filter for table filter rows (Pancake-style: calendar button → body-portal popover w/ preset rail Today/Yesterday/Last 7·14·30 days/This month/Last month + Start/End inputs + dual-month calendar + Clear/Close/Apply — applies agad, no Search click). Used by: Fulfillment (all date cols), Sales Tracker (`COL_DATE_RANGE`), Book Keeping posted date, Reimbursement date, Utility date + due date (due filter became a RANGE: `dueFrom`/`dueTo` replaced `due`), Purchase Order issue date, Unit Codes date created. Wire pattern: `onApply` sets BOTH draft + applied filter state + `setPage(1)`.
- `fmtPeso(n)` is a **page-local helper** in `src/app/(app)/business/dashboard/page.tsx` only — not exported from utils. Other pages (Sales Tracker, personal dashboard) use `formatCurrency` from `src/lib/utils.ts`. When adding currency display, use `formatCurrency` from utils unless working directly inside the business dashboard page. Never write ₱ via PowerShell string ops (double-encodes UTF-8 and corrupts the symbol) — always write it through the Write tool or Edit tool.
- Card heights: `h-[78px]`, amounts: `text-2xl font-bold`, labels: `text-[11px] uppercase tracking-wider`. **Mobile:** dashboards drop to 2 columns / `h-[70px]` / `text-lg` via `sm:` prefixes (Aug 5 2026 sweep) — never a bare `grid-cols-3`, the peso amounts overflow at 375px.
- ⚠️ **A table inside `overflow-x-auto` needs a `min-w-[…]`, and every pill needs `whitespace-nowrap`.** `w-full` alone makes the table obey the container instead of scrolling, so on a phone or iPad the columns squeeze until each cell wraps — and a pill whose text wraps splits into two overlapping halves ("Facebook Ecom" became "Facebook" stacked on "Ecom"). Reported live on Pages & Store; the same pair was missing on Ad Accounts. Give the table a min-width wide enough for its columns and let the wrapper scroll.
- ⚠️ **A horizontal strip needs `overflow-y-hidden`, not just `overflow-x-auto`.** Setting one axis to `auto` makes the browser compute the other as `auto` too, so the element becomes a scroll container in BOTH directions. Tab strips whose buttons carry `-mb-px` (or any element a pixel past the box) then get a real, draggable vertical scroll — reported live on the Facebook Ads tabs, on desktop and phone. Pair it with `overscroll-x-contain` so the sideways drag doesn't chain into the page or the browser's back gesture. Applied on: the Facebook Ads tab strip, its Ads Manager level tabs, and the business dashboard's date-basis filter row.
- Global CSS classes in `src/app/globals.css`: `.page-title` (page headings), `.scrollbar-dark` (dark sidebar scrollbar)
- **Dark mode is a CSS layer, not `dark:` variants** (`globals.css` `.dark` block — 2,329 hardcoded light utilities across 78 files made per-class edits untenable). Utility classes are overridden under `.dark` (NOT the `--color-*` tokens: `text-white` and `bg-white` share a token, and coloured stat cards would get dark text). ⚠ Tinted badge selectors MUST be `[class~="bg-blue-50"]` (exact token) — `[class*=]` substring-matches `bg-blue-500` and blacks out every coloured stat card (happened Aug 13 2026). Toggle = `ThemeToggle` in the Topbar (localStorage `pesowise_theme`), applied pre-paint by an inline `<head>` script in the root layout (no white flash); first visit follows OS preference. Recharts dark rules live in the same block (SVG presentation attrs lose to CSS). ⚠ **Slash-opacity is a DIFFERENT class token:** `.dark .bg-slate-50` does not touch `bg-slate-50/50`, which stayed near-white over the dark card and showed up as a pale band on the Ads Manager Campaigns · Ad Sets · Ads strip (Aug 14 2026). Each level in real use is spelled out (`/50 /60 /70` for slate-50, `/60 /70 /95` for white, plus the Skeleton's slate-200/300) — **deliberately NOT `[class*=]`**, which would also hit `hover:bg-slate-50/70` and paint it while un-hovered. Low-alpha overlays (`bg-white/5 /10 /20 /25`) are excluded on purpose: they are veils over coloured gradients (landing page, RTS, ChannelNet) and are supposed to stay white. The same hole exists for **tinted** slash-opacity classes — `[class~="bg-blue-50"]` does not match `bg-blue-50/40` — and that one is app-wide, not cosmetic: `hover:bg-blue-50/40` is the row hover in ~18 tables, so every hovered row flashed pale blue in dark mode. Covered now (`bg-blue-50/40 /50 /60`, `bg-red-50/60`, `bg-amber-50/40`, `hover:bg-blue-50/30 /40`, `hover:bg-slate-50/60 /70`) with the same `color-mix(currentColor, --dk-surface)` formula as the solid tints. **`.dark` also sets `color-scheme: dark`** so the browser paints what CSS can't reach — scrollbars, native `<select>` popups, spinners, autofill; without it a pale scrollbar cut through the dark panels. ⚠ **`-100` is a BADGE, `-50` is a PANEL — different jobs.** A ROAS pill (`bg-emerald-100 text-emerald-800`) tinted at 16% of its own text colour separates from the card by only 1.26–1.41, so it stops reading as a pill. A stronger tint cannot fix it: moving the background toward the text colour *lowers* text contrast (measured — 26% → pill 1.82 but text 5.36; 34% → pill 2.25 but text 4.34, past AA). The fix is a **ring, not a colour**: `-100` gets `box-shadow: inset 0 0 0 1px color-mix(currentColor 45%, transparent)` over a 20% fill, drawing the pill edge without touching fill or text — and being inset it adds no layout. Measured after: green 6.26, amber 6.54, rose 4.66, all ringed; `-50` panels untouched. `text-indigo-*` was brightened to `#a5b4fc` (`#818cf8` measured 4.16 inside a ringed pill). ⚠ **Text `-800` shades need remapping too** (34 usages, 21 files): alert panels are `bg-rose-50 text-rose-800`, so covering only 600/700 left dark text on a darkened panel — measured L≈35 on L≈15, effectively unreadable. ⚠ **`text-slate-300` is NOT remapped and is therefore BRIGHT in dark mode** — brighter than real values beside it; do not use it for muted placeholders (a first measurement said 1.13, but that was a `lab()` parsing bug in the probe, not the CSS).
- **PWA:** `src/app/manifest.ts` + icons in `public/` (generated from the green "P" mark, incl. maskable variants) make the app installable (desktop + phone). `start_url=/business/dashboard`, standalone display.
- The sidebar is `h-screen` with `overflow-y-auto` on the nav — keeps it scrollable without overflowing the viewport
- Stale `.next` cache causes hydration mismatches after large style changes. Fix: stop server → `Remove-Item -Recurse -Force D:\Claude Files\pesowise\.next` → restart + hard refresh browser
- ⚠️ **Verifying a `globals.css` change against the running dev server will lie to you.** Turbopack keeps compiled CSS in `.next/dev` and does not always rebuild it — a rule added minutes ago simply is not there, and `getComputedStyle` reports the *old* value with total confidence (burned an hour on Aug 14 2026). `Remove-Item -Recurse -Force .next\dev` → restart the server → reload → re-measure. Note also that **`document.styleSheets[].cssRules` is empty in this browser** (cross-origin), so selector inspection is useless; computed style on a probe element is the only signal that works. And when checking the built bundle, search for the **minified** form — Lightning CSS rewrites `[class~="bg-blue-50/40"]` to `[class~=bg-blue-50\/40]`, so grepping the quoted source form returns a false negative.

### Sales Tracker specifics (`src/app/(app)/business/ecommerce/sales/page.tsx`)

The Sales Tracker uses `phase=rows` on the `/api/pancake/orders` route. This phase skips aggregates, paginates all orders with `ROW_FIELDS` (slim payload), and returns `{ success, phase:"rows", rows }` where `rows` is the output of `mapOrderRow()` in `route.ts`.

**Critical field mappings** (verified against live API — do not "simplify"):
- **Shipped Out** = `time_send_partner` (top-level field). `partner_inserted_at` is a **filter param** sent to the API, NOT a field returned in order objects — using it as a response field always gives blank.
- **Parcel Status** (courier) ≠ **Order Status** (process). They are separate columns. Parcel Status reads `partner.partner_status` → `PARTNER_STATUS_LABEL` map → latest `extend_update[].status` → "Not Available".
- **Order Status** raw values from Pancake are lowercased non-canonical strings. Normalize via `ORDER_STATUS_ALIAS`: `"submitted"→"Confirmed"`, `"packing"→"Packaging"`, `"canceled"→"Cancelled"`, `"waiting for pickup"→"Waiting for Pick Up"`, etc. `normalizeOrderStatus()` applies the alias map with Title-Case fallback for unknown values.
- **Parcel Update** = max of `last_update_status_at`, `partner.extend_update[].update_at`, fallback `updated_at`.
- **Parcel Qty** = count of **distinct product names** in `items` (`new Set(items.map(name)).size`). Not total units.
- **Courier** = `partner.partner_name` trimmed — never fall back to raw `partner_id` (numeric ID pollutes the dropdown).
- **Retention By** (field key `retention_by`, was `intern_name` — fully renamed everywhere). Reads "retention" tag → `creator.name` → tag editor → `last_editor`.
- **Verifier** / **Upsell By**: blank (not "-") when the order has no matching tag.
- **Shift**: always "Not Available" — Pancake has no shift/staff schedule data.
- **CSR** = `creator.name` (the staff who CREATED/encoded the order in Pancake), fallback `last_editor.name`, else **"System"** (storefront/API orders with no staff encoder). `csr_id` tracks the Pancake user ID. `mapOrderRow` maps this — it was previously unmapped (blank for synced orders).

**CRITICAL — row dates must be Philippine-time (`toPHDate`)**: `encoded_date` / `date_added` (→ `order_date`) / `shipped_out_date` are computed by `toPHDate()` (UTC+8 conversion), NOT a raw `inserted.slice(0,10)`. The server's date-window filter (`toUnix`) is PH-time; if rows kept UTC dates, orders created 12am–8am PH (UTC = previous day) get dropped by the client-side `order_date` filter — the "Today shows fewer orders than Pancake" bug. (The `byDate` aggregation already PH-converts; only the rows path needed this.)

**Price (Upsell) via localStorage baseline** (`localStorage` key `pesowise_order_baseline`):
- Pancake has no price history. While an order has no Upsell tag, snapshot its `total_price` keyed by order UID.
- When Upsell tag appears: `price_upsell = current − baseline`, `price_initial = baseline`, `price_final = current`.
- Orders already upselled before the tracker first loaded have no baseline → Price (Upsell) stays blank. This is unavoidable.
- Retention orders (Retention tag, no Upsell tag) show full amount in Initial/Final and blank Upsell — they are NOT treated as upsell.

**`ROW_FIELDS`** — the curated field list sent as `fields[]` to slim the Pancake payload:
`id, items, shipping_address, bill_full_name, bill_phone_number, total_price, cod, partner_fee, shipping_fee, partner, status, status_name, inserted_at, created_at, partner_inserted_at, bank_payments, updated_at, last_update_status_at, time_send_partner, tags, last_editor, marketer, creator`. If a column goes blank, check this list first.

**Column filter row** drives the Pancake fetch window: `colFilters["order_date__from"]` and `colFilters["order_date__to"]` are passed as `from`/`to` to `fetchPageRows()`. Changing those values triggers a re-fetch. Other column filters (courier, order_status, etc.) filter client-side only.

**Dropdown strategy**: Order Status uses a fixed canonical 9-value list (`ORDER_STATUS_OPTIONS`). Courier, Parcel Status, MOP, Page, Platform are data-derived (unique values from loaded rows). Never swap these — order status raw values are non-canonical and can't be used as the option list.

**`useHoverTip` / `ToggleChip`**: `useHoverTip(tip?)` is a hook that returns `{ref, tip}` for a 2-second-delay tooltip portaled to `<body>`. `ToggleChip` wraps a toggle-column chip with an optional tooltip. Tooltips belong on the **column toggle chips** (the `ToggleChip` components), NOT on table column headers.

**`ORDER_STATUS_BADGE`**: soft-background colored pill badges rendered only in table cells, not in the dropdown. Each status has a distinct `bg-*/text-*` color pair.

**Tags limitation**: Pancake `tags[]` officially only exposes `{id, name}`. Per-tag `editor`/`timestamp` are read defensively (spec is incomplete vs live response). All tag-derived columns (Verifier, Upsell By, Retention By, Reserve Date) are re-derived live on every fetch — not persisted anywhere.

**Stock legend + Orders page filter**: below the toggle chips sits a 🟥 Out of stock / 🟧 Low on stock legend and an "Orders [ALL ▾]" dropdown (filters the table to one page's orders; included in Clear Filters). The Order column cell is wired to a **dormant `stockStatus()` stub** (returns "" until the Inventory/Stocks module exists — then wire it to per-item stock and the red/orange text activates via `TODO(warehouse)` marker).

### Send orders to courier → books the real waybill (`api/pancake/orders/send-courier/route.ts`)

Fulfillment's "Send orders to courier" makes SPX/J&T actually generate a waybill. The shape of
this request was **recorded off the POS**, not guessed — hook `XMLHttpRequest` on
`pos.pancake.ph`, do one real Quick update, read the payload. Redo that if Pancake changes.

- **Endpoint is `POST /shops/{shop}/orders/update_multiple_orders`** — a bulk endpoint, not
  `PUT /orders/{id}`. Body is **form-encoded** with `orders[0][...]` keys, not JSON. Reachable on
  the public API with an `api_key` (it answers 400 to an empty payload; `orders/send_to_courier`
  and `orders/bulk_update` both 404 — they don't exist).
- **`partner_id` alone does NOT book anything.** It only writes the courier *name* onto the order.
  The order then shows a courier and moves to Waiting for Pick Up with **no tracking number**, and
  the API still answers success. That was the original bug — the ERP reported "Success" while the
  warehouse had no waybill to print.
- **The switch that books is `is_send_to_{courier}_phi`:**
  - SPX (partner 125): `is_send_to_spx_phi`, `is_free_ship_spx`, `is_spx_post`, `note_spx`,
    `allow_mutual_check_spx`, `allow_try_on_spx`, `pickup_time_spx[0]` (unix ts) + `[1]` (range id)
  - J&T (partner 10): `is_send_to_jnt_phi`, `payment_jnt_phi: "PP_PM"`, `is_drop_off_jnt_phi`,
    `signpart_jnt_phi`, `insurance_services_jnt_phi`
- **Payload is deliberately minimal** (id + partner + the order's *current* status + courier flags). The POS sends ~294
  fields because it holds the whole order client-side; the public API returns only ~106 and leaves
  some blank (`shipping_address`). Echoing that thin copy back would wipe data **if** the endpoint
  replaces rather than merges. It merges — confirmed on a live order — but the route still
  snapshots before/after and aborts loudly if any of `customer_name` / `shipping_address` /
  `order_item` / `final_price` / `contact_no` / `items` goes from filled to empty.
- **Booked is verified, not assumed — and the waybill is the ONLY proof.** After the write the order
  is re-read and `partner.extend_code` / `tracking_id` (= the tracking number) must be non-empty.
  `partner.service_partner` is **not** acceptable evidence: it is populated from the `partner_id` *we
  ourselves* wrote, so treating it as proof made every rejected order read as booked. If the order
  can't be re-read at all the route says "not verified" rather than guessing (it used to raise a
  false data-loss alarm in that case).
- **The status is advanced in a SEPARATE request, only after a waybill exists.** This is the
  out-of-delivery-zone fix (user, Aug 3 2026): SPX accepts the update, returns success, and creates
  **no waybill** when the address is outside its zone. Because `status: 9` used to ride along in the
  same booking request, the order flipped to Waiting for Pick Up anyway — a parcel the warehouse
  could never ship. Now the booking request writes back the order's *existing* status (present so a
  replace-style endpoint can't null the field, but never advanced), and `PUT {status: 9}` runs only
  after a tracking number is confirmed. A rejected order therefore **stays in Packaging** and stays
  in the Fulfillment queue.
- **ODZ is named when it can be.** On a no-waybill result the route scans the response and the
  `partner` object for the rejection text (`ODZ_RE` — "out of delivery zone/range/coverage/area",
  "not serviceable", …) and reports `odz: true` plus the courier's own wording. When the wording is
  unrecognised it still fails, just with the generic "rejected, no waybill created" message —
  **the pass/fail decision never depends on matching the text**, only on the waybill.
  ⚠ The exact ODZ response body has **not** been captured off a live rejection yet. If you want the
  message to quote SPX verbatim, record one the same way the payload was recorded.
- **Failed orders stay checked** when you close the progress modal, so an SPX-ODZ batch can be
  re-sent to J&T in one click instead of being hunted down row by row.

### Finance adspent model (changed — read before touching Income Statement)

- **Adspent = actual FB Paid charges** (`fb_paid_charges`, filtered by `paid_date` in range), NOT the Meta insights estimate and NOT the manual `is_adspent` bookkeeping debits. The user wanted real money-out only ("sa fb ads lang muna").
- Paid amounts are **VAT-inclusive**, so they are split: `Adspent (ex-VAT) = fbPaid ÷ 1.12`, `VAT = fbPaid − Adspent`.
- **The 12% VAT is OPEX, not a gross-profit deduction.** `Gross Profit = Revenue − Adspent(ex-VAT) − COG − Shipping`; `OPEX = bookkeeping OPEX + VAT`; `Profit & Loss = Gross Profit − OPEX`. Finance Overview shows ADSPENT ex-VAT with a **separate "12% VAT" card**; VAT counts toward *Total OPEX + Revolving* but is **excluded from the Revolving Fund** card.
- **No OPEX double-count:** paid charges post to Book Keeping under the non-default `Facebook Ads Billing` type, which is not OPEX-flagged and whose account has `is_adspent: false`, so those ledger rows only reduce bank funds.
- **Warehouse Inventory** row = `Σ(cog × itemRemaining)` over non-deleted/non-archived items, plus a piece count. It is a current balance (the date picker does NOT apply) and is deliberately kept OUT of Projected Company Funds — stock is not cash.

### Testing & Scaling tracker (`src/components/business/ads/ScalingTracker.tsx`, tabs sa `ads/facebook/page.tsx`)

Testing and Scaling are registered-only — that's their point ("para malinis"); Monitoring is the opposite and shows everything.

- **Monitoring specifics:** every campaign with spend **this month** (not the rolling 30 days — a campaign that only ran last month is noise there); each row carries a month-to-date line (spend / value / ROAS / purchases / CPP) from the 1st. **`isScaling = !isMonitoring`** is the flag that switches "registered only" off. `regByAdset` is deliberately left EMPTY in this mode even though it shares `level="campaign"` with Scaling — otherwise a campaign registered in Scaling would drag its Scale, Undo and unregister buttons into a tab where **Kill is the only action**. **"SCHEDULED" AND "COMPLETED" COME FROM `start_time` / `stop_time`, NOT FROM STATUS** — `effective_status` does not look at the clock: a campaign created today that starts Monday comes back `ACTIVE`, so it showed **Active** while delivering nothing (owner-reported, Aug 17 2026). Placement in the delivery ladder is the part to preserve: own-pause, rejection, parent-paused and billing all **outrank** Scheduled (a paused scheduled ad set reads "Off", matching Ads Manager), while Scheduled **outranks** the kids-off check and learning — flagging "Ad set off" or "Learning 0/50" on something that hasn't started yet is a false alarm. **Scheduled is green, the same tone as Active** — owner's ruling, Aug 17 2026, and a deliberate departure from Meta (Ads Manager greys it). The reasoning: it is switched on and correctly set up, with nothing to do until its hour comes, so grey — which here means "will not run" — would misread it. **Completed stays slate**, because that one really is finished. Unparseable or missing times never invent a state. ⚠ **THE CAMPAIGN HAS NO CLOCK OF ITS OWN — THE AD SET DOES** (owner, Aug 21 2026): a campaign can carry a `start_time` that already passed (or none) while every switched-on ad set under it starts next week, so the ad set read **Scheduled** and the campaign above it read **Active**. The route returns **`kidsStart`** = the EARLIEST start among switched-on ad sets — if the earliest is still ahead, they all are, which is the whole answer in one field. Blank when any switched-on ad set has no readable time (never guess Scheduled), and blank when nothing is switched on, so an all-off campaign still reads "Ad set off". **PREFETCH FROM APP OPEN** (`src/lib/use-ads-prefetch.ts`, mounted as `<AdsPrefetcher />` in the app layout — so it runs on EVERY page, not just Facebook Ads). ⚠️ **TTL decides when to RE-PULL, never what to SHOW.** Every boot path (`dashBoot`, the Ads Manager `rows` initializer, `lvlFromCache`, the tracker's `applyCached`) reads the cache **without an age check** — a two-hour-old number beats a blank screen, and the revalidate swaps it silently. - **FIFO batch costing (BUILT)** (`src/lib/product-batches-store.ts`, migrations `0019`/`0020`) — a product item no longer carries one COG. Each delivery is a **batch** (`product_batches`: qty, cog, received_date, consumed) and every deduction eats the **oldest batch first**, so a shipment's COGS is the price actually paid for those exact pieces. Averaging was rejected: it retroactively re-prices goods already sold.
  - `planFifo()` is **pure and exported** — it returns the plan (which batch, how many, at what cog) without writing, so it is unit-testable and the caller can inspect before applying.
  - ⚠️ **Short stock never blocks.** If the batches can't cover the quantity, `planFifo` consumes what exists and reports `short` — the parcel really left, so the count must still drop; only the *costing* is incomplete, and that is surfaced (`cogs_short`) rather than hidden.
  - ⚠️ **Two sources of quantity exist by design**: `product_items.goods/released` (the count) and the batches (the cost). Receive Stock writes both; every deduction eats both. `reconcile()` compares them and Product Items shows an amber banner when they drift — a silent gap means a wrong inventory valuation.

This is what makes a correct RTS restock possible later: look the parcel up by tracking number and return the pieces to the *same* batch they came from. Without it the information is gone the moment the page reloads.

Gated by `restocked_at` with the same conditional-update trick as `deducted`, so two devices can't restock one parcel twice.
    - ⚠️ **Only GOOD pieces return.** Damage/loss stay consumed: they left, can never be sold, and their COGS is already expensed. Returning them would show sellable stock that does not exist. `goodQtyOf()` reads the RTS check counts; an unchecked parcel is assumed all-good and the confirm modal says so.

## Persistence — Supabase is the source of truth (localStorage is a read cache)

**This section used to say "no Supabase wiring yet". That is obsolete.** Migrations `0001`–`0031` live in `supabase/migrations/` and every module now reads/writes Supabase; `localStorage` (`pesowise_*`) survives only as a **same-session read cache** for instant paint, migrated up once on first load. Store shape: `use client` hook → paint from cache → fetch from Supabase (`.eq("business_id", …)`) → `normalize()` legacy/partial rows defensively → write through on every mutation.

- Single-business deployment: `getBusinessId()` = `businesses.select("id").limit(1)` — it is `"use client"` and **NOT usable server-side**. In scripts/API routes use `createSupabaseServerClient()` (service role) + the same one-liner.
- RLS on every table: `owner_id = auth.uid()` OR `public.is_business_member(business_id)`. Copy an existing policy verbatim when adding a table.
- **Migrations are run by the USER** in the Supabase SQL Editor — hand them the SQL (clipboard via PowerShell `Set-Clipboard` is the established flow) and wait for confirmation before assuming a table exists.
- ⚠️ **Check for name collisions before naming a table.** `subscriptions` was already taken by a Supabase starter template, which failed the whole migration with `42703: column "business_id" does not exist` — the `create table if not exists` silently skipped, then the index/policy hit the pre-existing table. - Supabase **Storage** is used for the first time by Problem Management (`problem-files` bucket, 50MB/file). Everything else still stores images as downscaled data URLs.

The Claude Code **preview panel has isolated localStorage** and its **auth cookie expires** (~1h → redirects to `/login`), so live UI usually can't be driven from here — verify with `tsc --noEmit` + `npm run build` + Node scripts against Supabase, and ask the user to confirm in their authenticated browser.
