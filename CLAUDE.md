# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # Start dev server (Next.js + Turbopack on port 3000)
npm run build      # Production build
npm run lint       # ESLint
```

> **Windows SSL note:** The dev script runs `cross-env NODE_OPTIONS=--use-system-ca next dev`. This is required because Node.js's built-in fetch (undici) does not trust the Windows system certificate store by default, which causes all Supabase calls to fail with `UNABLE_TO_VERIFY_LEAF_SIGNATURE`. Do not remove `cross-env NODE_OPTIONS=--use-system-ca` from the dev script.

### Auth flow

Auth is **cookie-based, not Supabase SSR**. The login API route (`/api/auth/login`) calls `signInWithPassword` and manually sets `sb-access-token` and `sb-refresh-token` cookies. The middleware (`src/middleware.ts`) checks for `sb-access-token` on every non-public route.

- Use `createSupabaseBrowserClient()` (anon key) for auth operations like `signInWithPassword`
- Use `createSupabaseServerClient()` (service role key) for admin operations like `createUser` or direct table writes
- The app layout (`src/app/(app)/layout.tsx`) reads the cookie manually and calls `supabase.auth.setSession()` to rehydrate the client-side session
- **The cookie is REWRITTEN on every app load + on `TOKEN_REFRESHED`** (`writeSessionCookies` in the app layout). Fixed Aug 6 2026: the cookie had a 7-day maxAge and was only set at login, while the Supabase client silently refreshed the token in localStorage against a 30-day refresh token — so exactly 7 days after login the cookie died with the session still valid: the UI looked signed-in (name comes from localStorage) but every API call failed.
- **Middleware answers API routes (`/api/*`) with a JSON 401 `{errorCode:"SESSION_EXPIRED"}`** instead of redirecting to `/login` — `fetch()` silently follows redirects, so users were getting `Unexpected token '<', "<!DOCTYPE"... is not valid JSON` on every page instead of "Session expired". Page routes still 307 to `/login`. `/manifest.webmanifest` + icons are PUBLIC_PATHS (a login-redirected manifest kills the PWA "Install app" prompt).

### Shared data pattern (Pages & Store)

Pages & Store data flows through a React Context, **not** direct imports:

- `src/lib/pages-store.tsx` — `PagesProvider` (mounted in `src/app/(app)/layout.tsx`) holds the live list in state. Source of truth = Supabase `store_pages`; `localStorage` `pesowise_pages` is a same-session read cache that paints instantly, then gets refreshed.
- Consume with `usePages()` (full CRUD) or `useActivePages()` (non-archived only). The business dashboard and ROAS Tracker both read pages via `useActivePages()` — this is how a store's Pancake credentials reach those modules.
- `src/lib/pages-data.ts` only defines the `PageStore` type and the original seed array (now only used as a first-run fallback).
- ⚠️ **`useActivePages()` returns a FRESH array every render.** Key fetch effects off a value string (e.g. `pagesKey`), never off array identity, or you get an infinite fetch loop.

A page is "connected" to the dashboard/ROAS when it has both `api_key` and (`pancake_page_id` or `shop_id`).

### Pancake POS integration

The business dashboard and ROAS Tracker pull real order data from Pancake POS Open API via the server-side proxy `src/app/api/pancake/orders/route.ts` (keeps credentials server-side, avoids CORS). `src/app/api/pancake/debug/route.ts` is a diagnostic endpoint for inspecting raw Pancake responses.

Non-obvious facts (verified against a live shop — do not "simplify" these away):

- **Base URL / endpoint:** `https://pos.pages.fm/api/v1/shops/{SHOP_ID}/orders`. Auth is the `api_key` query param. The client passes the shop ID as the `page_id` query param to our route.
- **Date filter:** `startDateTime`/`endDateTime` are **Unix timestamps** (not `from_date`/`to_date`), plus `updateStatus=inserted_at`. `toUnix()` converts `YYYY-MM-DD` to a PHT (UTC+8) timestamp. Pagination uses `page_number` + `page_size` (max 100), not `page`.
- **`status` is a number, `status_name` is the string.** Verified primary status codes: `0` new, `1` confirmed, `2` shipped, `3` delivered, `4` returning (For Return), `5` returned, `6` canceled (Unfulfilled), `7` removed (excluded from totals), `8` packaging, `9` waiting-for-pickup, `11` restocking.
- **In Transit / On Delivery are courier sub-statuses, not primary statuses.** They live in `order.partner.partner_status` (`on_the_way` = In Transit, `out_for_delivery` = On Delivery, `undeliverable` = problematic). These can't be filtered server-side, so they're tallied by paginating all orders.
- **Sales = the `cod` field.** ⚠️ **COUNTS and MONEY come from different places, on purpose.** Counts use the one-row `filter_status[]` aggregates (`total_entries` — authoritative, not pagination-limited). **Money must NEVER come from `aggs.cod.value`**: it is summed server-side by Pancake, so the 100× SCALE guard (which needs per-order item prices) cannot reach it. Live proof (Aug 6 2026): the same 83 parcels read **₱146,512** via the aggregate but **₱47,710** via pagination — one order storing ₱998 as ₱99,800 inflated everything 2.6×. All displayed money therefore comes from `response.exact`, computed per-order in `phase=full` where `descale()` applies. `fetchStatusAgg`'s `sales` field is kept only because `byDate`/ROAS predate this; treat it as diagnostic, not displayable.
- **`response.exact`** (phase=full) = per-status counts + descaled money, **cancelled (status 6) excluded** — the same rule `byDate` uses, so the TOTAL SALES card and its breakdown modal always agree. Also carries `rescaledOrders`/`rescaledExcess` (surfaced as an amber banner — the 100× correction is never silent) and `response.truncated` (range exceeded `MAX_PAGES`×100 = 20,000 orders → money is UNDERSTATED, red banner).
- **`?status=6,8`** limits phase=full pagination to given statuses — how "Unfulfilled / Last Month" gets descaled money for a whole month without paginating every order in it.
- **Dashboard card formulas:** Total RTS = returning + returned; **Unfulfilled = packaging (status 8)** — not canceled; Fulfilled = delivered + shipped + waiting-for-pickup. **Total Sales excludes cancelled** (user decision, Aug 7 2026 — cancelled is not income).
- **Dashboard paint order:** phase 1 paints COUNTS only (instant, aggregate-derived); every peso figure shows a spinner until phase 2 lands. Showing the aggregate amount first and correcting it later was rejected — a finance card that jumps from ₱154,778 to ₱55,976 destroys trust more than a 2-second wait.

### Sales Tracker specifics (`src/app/(app)/business/ecommerce/sales/page.tsx`)

The Sales Tracker uses `phase=rows` on the `/api/pancake/orders` route. This phase skips aggregates, paginates all orders with `ROW_FIELDS` (slim payload), and returns `{ success, phase:"rows", rows }` where `rows` is the output of `mapOrderRow()` in `route.ts`.

**Critical field mappings** (verified against live API — do not "simplify"):
- **Shipped Out** = `time_send_partner` (top-level field). `partner_inserted_at` is a **filter param** sent to the API, NOT a field returned in order objects — using it as a response field always gives blank.
- **Parcel Status** (courier) ≠ **Order Status** (process). They are separate columns. Parcel Status reads `partner.partner_status` → `PARTNER_STATUS_LABEL` map → latest `extend_update[].status` → "Not Available".
- **Order Status** raw values from Pancake are lowercased non-canonical strings. Normalize via `ORDER_STATUS_ALIAS`: `"submitted"→"Confirmed"`, `"packing"→"Packaging"`, `"canceled"→"Cancelled"`, `"waiting for pickup"→"Waiting for Pick Up"`, etc. `normalizeOrderStatus()` applies the alias map with Title-Case fallback for unknown values.
- **Parcel Update** = max of `last_update_status_at`, `partner.extend_update[].update_at`, fallback `updated_at`.
- **Parcel Qty** = count of **distinct product names** in `items` (`new Set(items.map(name)).size`). Not total units.
- **Courier** = `partner.partner_name` trimmed — never fall back to raw `partner_id` (numeric ID pollutes the dropdown).
- **Retention By** (field key `retention_by`, was `intern_name` — fully renamed everywhere). Reads "retention" tag → `creator.name` → tag editor → `last_editor`.
- **Verifier** / **Upsell By**: blank (not "-") when the order has no matching tag.
- **Shift**: always "Not Available" — Pancake has no shift/staff schedule data.
- **CSR** = `creator.name` (the staff who CREATED/encoded the order in Pancake), fallback `last_editor.name`, else **"System"** (storefront/API orders with no staff encoder). `csr_id` tracks the Pancake user ID. `mapOrderRow` maps this — it was previously unmapped (blank for synced orders).

**CRITICAL — row dates must be Philippine-time (`toPHDate`)**: `encoded_date` / `date_added` (→ `order_date`) / `shipped_out_date` are computed by `toPHDate()` (UTC+8 conversion), NOT a raw `inserted.slice(0,10)`. The server's date-window filter (`toUnix`) is PH-time; if rows kept UTC dates, orders created 12am–8am PH (UTC = previous day) get dropped by the client-side `order_date` filter — the "Today shows fewer orders than Pancake" bug. (The `byDate` aggregation already PH-converts; only the rows path needed this.)

**Price (Upsell) via localStorage baseline** (`localStorage` key `pesowise_order_baseline`):
- Pancake has no price history. While an order has no Upsell tag, snapshot its `total_price` keyed by order UID.
- When Upsell tag appears: `price_upsell = current − baseline`, `price_initial = baseline`, `price_final = current`.
- Orders already upselled before the tracker first loaded have no baseline → Price (Upsell) stays blank. This is unavoidable.
- Retention orders (Retention tag, no Upsell tag) show full amount in Initial/Final and blank Upsell — they are NOT treated as upsell.

**`ROW_FIELDS`** — the curated field list sent as `fields[]` to slim the Pancake payload:
`id, items, shipping_address, bill_full_name, bill_phone_number, total_price, cod, partner_fee, shipping_fee, partner, status, status_name, inserted_at, created_at, partner_inserted_at, bank_payments, updated_at, last_update_status_at, time_send_partner, tags, last_editor, marketer, creator`. If a column goes blank, check this list first.

**Column filter row** drives the Pancake fetch window: `colFilters["order_date__from"]` and `colFilters["order_date__to"]` are passed as `from`/`to` to `fetchPageRows()`. Changing those values triggers a re-fetch. Other column filters (courier, order_status, etc.) filter client-side only.

**Dropdown strategy**: Order Status uses a fixed canonical 9-value list (`ORDER_STATUS_OPTIONS`). Courier, Parcel Status, MOP, Page, Platform are data-derived (unique values from loaded rows). Never swap these — order status raw values are non-canonical and can't be used as the option list.

**`useHoverTip` / `ToggleChip`**: `useHoverTip(tip?)` is a hook that returns `{ref, tip}` for a 2-second-delay tooltip portaled to `<body>`. `ToggleChip` wraps a toggle-column chip with an optional tooltip. Tooltips belong on the **column toggle chips** (the `ToggleChip` components), NOT on table column headers.

**`ORDER_STATUS_BADGE`**: soft-background colored pill badges rendered only in table cells, not in the dropdown. Each status has a distinct `bg-*/text-*` color pair.

**Tags limitation**: Pancake `tags[]` officially only exposes `{id, name}`. Per-tag `editor`/`timestamp` are read defensively (spec is incomplete vs live response). All tag-derived columns (Verifier, Upsell By, Retention By, Reserve Date) are re-derived live on every fetch — not persisted anywhere.

**Stock legend + Orders page filter**: below the toggle chips sits a 🟥 Out of stock / 🟧 Low on stock legend and an "Orders [ALL ▾]" dropdown (filters the table to one page's orders; included in Clear Filters). The Order column cell is wired to a **dormant `stockStatus()` stub** (returns "" until the Inventory/Stocks module exists — then wire it to per-item stock and the red/orange text activates via `TODO(warehouse)` marker).

### Add New Order → creates real Pancake orders

The Sales Tracker's "Add New Order" form CREATES orders directly in Pancake POS via two proxy routes (same `page_id`→shop URL convention + `api_key` query param + `classifyConn` error handling as the orders route):
- **`api/pancake/products/route.ts`** — `GET`, proxies `/shops/{shop}/products`, returns a flattened list of one entry per sellable variation `{product_id, variation_id, display_id, name, price}`. The product picker is page-dependent (loads after a Page is selected; lists only connected pages).
- **`api/pancake/orders/create/route.ts`** — `POST`, proxies `POST /shops/{shop}/orders`. NOT idempotent (no retries on ambiguous failures). No prices sent — Pancake derives totals from the variation; `status: 0` (New).
- **`api/pancake/geo/route.ts`** — `GET`, proxies Pancake's `/geo/provinces?country_code=63` / `/geo/districts` / `/geo/communes` (PH country_code = "63"). Drives **cascading address dropdowns** (Province → City → Barangay); the order's `shipping_address` carries the real `province_id`/`district_id`/`commune_id` + `country_code:"63"`. 1-hour cache.
- Removed Price/Shipping fields from the form (pricing is automatic from the product).

### Send orders to courier → books the real waybill (`api/pancake/orders/send-courier/route.ts`)

Fulfillment's "Send orders to courier" makes SPX/J&T actually generate a waybill. The shape of
this request was **recorded off the POS**, not guessed — hook `XMLHttpRequest` on
`pos.pancake.ph`, do one real Quick update, read the payload. Redo that if Pancake changes.

- **Endpoint is `POST /shops/{shop}/orders/update_multiple_orders`** — a bulk endpoint, not
  `PUT /orders/{id}`. Body is **form-encoded** with `orders[0][...]` keys, not JSON. Reachable on
  the public API with an `api_key` (it answers 400 to an empty payload; `orders/send_to_courier`
  and `orders/bulk_update` both 404 — they don't exist).
- **`partner_id` alone does NOT book anything.** It only writes the courier *name* onto the order.
  The order then shows a courier and moves to Waiting for Pick Up with **no tracking number**, and
  the API still answers success. That was the original bug — the ERP reported "Success" while the
  warehouse had no waybill to print.
- **The switch that books is `is_send_to_{courier}_phi`:**
  - SPX (partner 125): `is_send_to_spx_phi`, `is_free_ship_spx`, `is_spx_post`, `note_spx`,
    `allow_mutual_check_spx`, `allow_try_on_spx`, `pickup_time_spx[0]` (unix ts) + `[1]` (range id)
  - J&T (partner 10): `is_send_to_jnt_phi`, `payment_jnt_phi: "PP_PM"`, `is_drop_off_jnt_phi`,
    `signpart_jnt_phi`, `insurance_services_jnt_phi`
- **Payload is deliberately minimal** (id + partner + the order's *current* status + courier flags). The POS sends ~294
  fields because it holds the whole order client-side; the public API returns only ~106 and leaves
  some blank (`shipping_address`). Echoing that thin copy back would wipe data **if** the endpoint
  replaces rather than merges. It merges — confirmed on a live order — but the route still
  snapshots before/after and aborts loudly if any of `customer_name` / `shipping_address` /
  `order_item` / `final_price` / `contact_no` / `items` goes from filled to empty.
- **Booked is verified, not assumed — and the waybill is the ONLY proof.** After the write the order
  is re-read and `partner.extend_code` / `tracking_id` (= the tracking number) must be non-empty.
  `partner.service_partner` is **not** acceptable evidence: it is populated from the `partner_id` *we
  ourselves* wrote, so treating it as proof made every rejected order read as booked. If the order
  can't be re-read at all the route says "not verified" rather than guessing (it used to raise a
  false data-loss alarm in that case).
- **The status is advanced in a SEPARATE request, only after a waybill exists.** This is the
  out-of-delivery-zone fix (user, Aug 3 2026): SPX accepts the update, returns success, and creates
  **no waybill** when the address is outside its zone. Because `status: 9` used to ride along in the
  same booking request, the order flipped to Waiting for Pick Up anyway — a parcel the warehouse
  could never ship. Now the booking request writes back the order's *existing* status (present so a
  replace-style endpoint can't null the field, but never advanced), and `PUT {status: 9}` runs only
  after a tracking number is confirmed. A rejected order therefore **stays in Packaging** and stays
  in the Fulfillment queue.
- **ODZ is named when it can be.** On a no-waybill result the route scans the response and the
  `partner` object for the rejection text (`ODZ_RE` — "out of delivery zone/range/coverage/area",
  "not serviceable", …) and reports `odz: true` plus the courier's own wording. When the wording is
  unrecognised it still fails, just with the generic "rejected, no waybill created" message —
  **the pass/fail decision never depends on matching the text**, only on the waybill.
  ⚠ The exact ODZ response body has **not** been captured off a live rejection yet. If you want the
  message to quote SPX verbatim, record one the same way the payload was recorded.
- **Failed orders stay checked** when you close the progress modal, so an SPX-ODZ batch can be
  re-sent to J&T in one click instead of being hunted down row by row.

### Finance adspent model (changed — read before touching Income Statement)

- **Adspent = actual FB Paid charges** (`fb_paid_charges`, filtered by `paid_date` in range), NOT the Meta insights estimate and NOT the manual `is_adspent` bookkeeping debits. The user wanted real money-out only ("sa fb ads lang muna").
- Paid amounts are **VAT-inclusive**, so they are split: `Adspent (ex-VAT) = fbPaid ÷ 1.12`, `VAT = fbPaid − Adspent`.
- **The 12% VAT is OPEX, not a gross-profit deduction.** `Gross Profit = Revenue − Adspent(ex-VAT) − COG − Shipping`; `OPEX = bookkeeping OPEX + VAT`; `Profit & Loss = Gross Profit − OPEX`. Finance Overview shows ADSPENT ex-VAT with a **separate "12% VAT" card**; VAT counts toward *Total OPEX + Revolving* but is **excluded from the Revolving Fund** card.
- **No OPEX double-count:** paid charges post to Book Keeping under the non-default `Facebook Ads Billing` type, which is not OPEX-flagged and whose account has `is_adspent: false`, so those ledger rows only reduce bank funds.
- **Warehouse Inventory** row = `Σ(cog × itemRemaining)` over non-deleted/non-archived items, plus a piece count. It is a current balance (the date picker does NOT apply) and is deliberately kept OUT of Projected Company Funds — stock is not cash.

### Testing & Scaling tracker (`src/components/business/ads/ScalingTracker.tsx`, tabs sa `ads/facebook/page.tsx`)

One engine, two modes decided by the owner's workflow (Aug 14 2026): **Testing = AD SET level** (register a new test, follow it from the day you register), **Scaling = CAMPAIGN level** (the 1-1-40+ Andromeda scaling campaigns — the CBO budget lives on the CAMPAIGN, so Scale 10%/20% targets the object that actually holds money). Registered-only on both tabs — that's the point ("para malinis").

- **Net ROAS convention:** `value × (1 − page RTS rate) ÷ (spend × 1.12)`. RTS rate = the page's (returning+returned)÷total over the same 30-day window from Pancake fast aggregates (~7–12% per page; there is NO per-adset RTS — stated in the UI). Gross shown alongside.
- **Registry** = Supabase `scaling_registry` (migrations `0024` + `0025`, **both applied Aug 14 2026**). `adset_id` = the Meta OBJECT id (ad set OR campaign per `level`); unique (business_id, adset_id); `scales` jsonb = every scale step `{date,pct,from,to,applied}` → "scale #3 · ₱600→₱950 (+58%)". `level='ad-moved'` rows are **markers, not registrations**: a winning ad the owner manually rebuilt in the scaling campaign via Ads Manager ("✅ Moved" in View ads; shared across the 3 buyers). Re-registering an unregistered object = fresh start (upsert resets date/budget/scales). Unregister sets `active=false` (history kept). **Orphan registrations** (object deleted, or a campaign saved as level='adset' by an older build — happened) are surfaced with a Remove button, never silently dropped.
- **Data:** one `series=1&level=adset|campaign` insights mode (30d × object daily rows, single Graph call per account) + rich meta for status/budget/created_time. ⚠ **The object LIST comes from the meta edge, not insights** — insights only returns objects that SPENT (measured: 72% of ad sets / 75% of campaigns would vanish, including anything created today). `budget` uses `ownBudget` only; in Testing, CBO ad sets resolve their campaign's budget via `budgetTarget()` (65% of their ad sets are CBO).
- **Rules** (editable sa Rules panel, localStorage `pesowise_scaling_rules` — per browser): scale = net ≥ 3.9 × 3+ straight days @ ≥₱500/day; kills = day net < 2.8 (11PM framing) / 0 sales by 9AM with spend / 3d net < 1.5 @ ≥₱2k bleeding / 3d CPP > ₱250; fatigue per AD = 2+ of freq ≥ 2.5, CTR −25%, CPM +20%, CPP +30% (last 3d vs prior 7d) → "refresh creative, don't kill". **48h cooldown after any scale** — neither killed nor re-scaled while delivery relearns. Auto-pause exists (master + per-rule opt-in + daily cap + undo, localStorage log) but is suggest-only by default and **only runs while the tab is open**.
- **Actions:** Testing rows get **Kill** (red, pauses the ad set; replaces Scale — a failed test dies, a winner is rebuilt in the scaling campaign by hand). Scaling rows get **Scale** (10%/20% modal → real `daily_budget` update via `api/fb/manage`; bulk via checkboxes; a CBO campaign shared by 2 selected ad sets is raised ONCE) + Pause now on kill rows. Drill-downs: Scaling = View ad sets + View ads off the campaign; Testing = View ads off the ad set; ad rows have Kill + (Testing only) Move to Scaling marker. AI: `api/ai/scaling/route.ts` → `claude-opus-5` server-side (per-row opinion / morning brief / Ask AI; advise-only, house thresholds pinned in the system prompt).
- **Perf traps na totoong nangyari:** (1) the two tabs MUST have distinct `key` props — same component at the same tree position gets reused by React and the other tab's `adsets` state bleeds through; (2) load effects key off `liveKey` value-string with arrays read via refs — putting `useActivePages()`/accounts arrays in the deps recreated the Jul 9 infinite-refetch loop (browser ran out of sockets, everything "Failed to fetch"); (3) `MODEL_CACHE` (module-level, keyed level|liveKey|dates, 10-min TTL) makes tab returns instant — Refresh forces.
- ⚠️ **The distinct `key` from trap (1) means every tab switch REMOUNTS the tracker, so the cache has to survive an unfinished load.** Caching the result alone wasn't enough: switching tabs mid-pull started a SECOND full pull (21 accounts × 3 requests), the next switch a third, and nothing ever reached `MODEL_CACHE.set` — the bar sat at 0/21 forever (owner-reported Aug 14 2026). Fixed with **`MODEL_INFLIGHT` / `FATIGUE_INFLIGHT`**: a mount that finds a running pull for its `cacheKey` **awaits that promise** instead of starting its own, and follows `MODEL_PROGRESS` (module-level) so the joiner still sees a moving bar. - ⚠️ **`Row`/`Section` are declared inside the component, so they must be CALLED (`{Section({…})}`), never written as `<Section />`.** A component defined during render is a new type every render; React unmounts and rebuilds the whole list each time — 21 progress ticks meant 21 full rebuilds with the ad thumbnails re-downloading.

## Persistence — Supabase is the source of truth (localStorage is a read cache)

**This section used to say "no Supabase wiring yet". That is obsolete.** Migrations `0001`–`0021` live in `supabase/migrations/` and every module now reads/writes Supabase; `localStorage` (`pesowise_*`) survives only as a **same-session read cache** for instant paint, migrated up once on first load. Store shape: `use client` hook → paint from cache → fetch from Supabase (`.eq("business_id", …)`) → `normalize()` legacy/partial rows defensively → write through on every mutation.

- Single-business deployment: `getBusinessId()` = `businesses.select("id").limit(1)` — it is `"use client"` and **NOT usable server-side**. In scripts/API routes use `createSupabaseServerClient()` (service role) + the same one-liner.
- RLS on every table: `owner_id = auth.uid()` OR `public.is_business_member(business_id)`. Copy an existing policy verbatim when adding a table.
- **Migrations are run by the USER** in the Supabase SQL Editor — hand them the SQL (clipboard via PowerShell `Set-Clipboard` is the established flow) and wait for confirmation before assuming a table exists.
- ⚠️ **Check for name collisions before naming a table.** `subscriptions` was already taken by a Supabase starter template, which failed the whole migration with `42703: column "business_id" does not exist` — the `create table if not exists` silently skipped, then the index/policy hit the pre-existing table. Prefix when in doubt (`finance_subscriptions`).
- Supabase **Storage** is used for the first time by Problem Management (`problem-files` bucket, 50MB/file). Everything else still stores images as downscaled data URLs.

The Claude Code **preview panel has isolated localStorage** and its **auth cookie expires** (~1h → redirects to `/login`), so live UI usually can't be driven from here — verify with `tsc --noEmit` + `npm run build` + Node scripts against Supabase, and ask the user to confirm in their authenticated browser.

## Shared client libs (use these — do not re-implement per page)

- **`src/lib/pancake-cache.ts`** — `cachedJson(url, { force })`. Module-level 15-min response cache that **survives client-side navigation and clears on hard refresh**, plus in-flight de-duplication. This is what stops the "every tab re-loads with a spinner" complaint: first visit fetches, revisits are instant, the Refresh button passes `force: true`. **Every Pancake fetch in the app routes through this** (warehouse dashboard, PPW, shipped-out, inventory dashboard, RTS, fulfillment, sales, business dashboard, adspent, `courier-live`). Do not add a raw `fetch("/api/pancake/…")`.
- **`src/lib/courier.ts`** — `courierOf(name, tracking)`, `courierTally()`, `COURIERS`, `COURIER_COLOR`. **We ship SPX and J&T only.** Resolution is name-first, then **tracking prefix** — this fallback is load-bearing: parcels that have a printed waybill but haven't been collected often come back with an EMPTY `partner.partner_name`, which used to dump hundreds of SPX parcels into "OTHER". Verified live: `SPEPH…` = SPX, `JT…` and long numerics (`980208157812`) = J&T. Four divergent local `courierLabel` copies were replaced by this — don't reintroduce one.
- **`src/components/business/Confidential.tsx`** — `<Confidential value>` (per-row 👁 reveal, masked `••••••••` by default) + `<ConfidentialToggle>` (page-level Show/Hide all). Used for **Supplier Store Name** in the Supplier table, Product Items table, and both View screens. ⚠️ It **replaces** the text rather than CSS-blurring it — a blur leaves the real value in the DOM. The mask is a **fixed length** so the name can't be guessed from it, the `title` tooltip is only attached when revealed, and the toggle is deliberately **not** persisted (a remembered "shown" is the same as no masking). Filters and Excel export still work on the real value — masking is display-only, not access control.
- **`src/components/business/Skeleton.tsx`** — `Skeleton`, `StatCardSkeleton`, `StatCardsSkeleton`, `TableSkeleton`, `ChartSkeleton`. Use while loading instead of rendering zeros (a card reading "0" is indistinguishable from real empty data).

## Scripts + scheduled tasks (`scripts/`, headless, service-role)

All are plain `.mjs` run by Node with no build step. They parse `../.env.local` for `NEXT_PUBLIC_SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`, and **fall back to `process.env`** when that file is absent (CI/cloud). Driven by **Claude Code scheduled tasks**, which only fire while the Claude Code app is open.

- **`roas-discord-report.mjs`** — Page ROAS report → Discord as a **PNG image** (HTML replica → headless Chrome `--screenshot` → `sharp.trim()` → multipart upload). `--window today|yesterday|mtd`, `--dry-run` (writes `scripts/_roas-report-preview.png`), `--no-fb`, `--text`, `--force`, `--slots`.
  - ⚠️ Chrome's `--screenshot` is only as large as `--window-size`, so a wide table **silently crops**. The layout is measured first (`--dump-dom` + a `data-size` attribute) and the viewport sized to it.
  - ⚠️ Runs **snap to their scheduled slot** (`SLOTS_MIN` = 9/12/3/6/9PM + 11:50PM). A delayed run still stamps "9:00PM edition (data as of 9:55PM PHT)", and a post-midnight EOD run closes the day it was chasing. **Keep `SLOTS_MIN` in sync with the cron.**
  - ⚠️ Dedup stamp `scripts/_roas-last-sent` (90 min) stops catch-up double-sends when several missed slots fire at once. `--force` bypasses it and does **not** write the stamp.
  - Config: `DISCORD_WEBHOOK_URL` in `.env.local` (webhook username "AI Agent Report"). ⚠️ `vercel env pull` overwrites `.env.local` and drops it — re-add.
- **`scaling-alerts.mjs`** — Testing/Scaling tracker signals → Discord (same webhook). Meant for 9AM PHT (no-sales check) + 11PM (low-ROAS) via Task Scheduler with `node --use-system-ca` (the user's machine needs system CAs for TLS; Claude's shell doesn't). **Notify-only — never pauses anything**; silent when there are no signals; uses the tracker's DEFAULT thresholds (per-browser Rules edits in localStorage don't reach it). ⚠ Not yet registered in Task Scheduler as of Aug 14 2026 — the schtasks commands are in the session log.
- **`subscriptions-bill.mjs`** — posts due `finance_subscriptions` to Book Keeping. `--dry-run`, `--date=YYYY-MM-DD`.
- **`problem-notify.mjs`** — queues Problem Management deadline reminders (7/3/1-day, due-today, daily-overdue) and sends the queue via **Resend**. Without `RESEND_API_KEY` the queue simply accumulates — that is not an error.
- **`fb-accounts.mjs` / `fb-charges-import.mjs`** — the FB Billing daily scrape (browser-driven, must stay local).

> **GitHub Actions was tried for scheduling and reverted.** Free cron ran **1h52m–2h35m late and skipped runs**; moving off `:00` to off-peak minutes only got it to ~73 min. ROAS reporting is back on local scheduled tasks. Anything needing the user's logged-in Chrome (FB Billing scrape, Gmail receipts) can never run in the cloud.

> **Dependency:** `xlsx-js-style` (SheetJS fork w/ cell styling) is used client-side for Book Keeping upload + finance/product exports. Based on SheetJS 0.18 (low-severity advisories) — fine for the user's own files; move server-side/exceljs if untrusted uploads ever matter.
